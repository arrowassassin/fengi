# Operations and maintenance

## Supported operating model

One Next.js Node 26 LTS server uses SQLite through pinned `better-sqlite3`. No external account, database service or credential is required for local operation. The production startup script resolves the default `.data/fengi.sqlite` path outside `.next/standalone`, so rebuilding does not replace progress. `FENGI_DATABASE_PATH` overrides it with an absolute path. Use a persistent **local** disk with restrictive ownership, adequate free space and backup storage; do not put the live WAL database on a network filesystem or an ephemeral serverless volume.

This is not a claim of enterprise launch readiness, horizontal scalability, high availability or a service-level guarantee. There is no email/account identity, trusted competitive ranking, managed monitoring or provisioned deployment. Do not add multiple independent SQLite volumes behind a load balancer: users would see divergent profiles. PostgreSQL (with equivalent transactional revision semantics) is the next step when shared multi-host writes are required.

## Runtime and security configuration

Set `FENGI_ORIGIN` to the exact public HTTPS origin behind a reverse proxy. Mutations require matching Origin, JSON content type and an application header; arbitrary forwarded headers are deliberately not trusted. Public binding (`FENGI_HOST=0.0.0.0`) also requires `FENGI_CLIENT_IP_HEADER`, naming a header containing exactly one client IP. The trusted ingress MUST overwrite that header and prevent direct access to the upstream port; otherwise callers can forge identities and evade limits. Missing or malformed configured IPs fail closed. Never point this setting at an unvalidated client-supplied forwarded chain. Without this setting, direct local access uses the request Host and protocol. The configured HTTPS origin enables Secure cookies; session cookies are always HttpOnly and SameSite=Strict. Empty provisional profiles expire after 24 hours; a saved game or recovery code promotes the profile and renews sessions for 180 days. Terminate TLS at the approved host/proxy and reject unknown hosts there. Apply ingress request/connection limits and timeouts, process restarts, OS patching and disk alerts. A deployment destination and its access credentials remain necessary before deployment; none were supplied or provisioned.

The public save API limits bodies to 32 KiB, validates session identity and frozen game invariants, and recomputes summaries/completion. Each profile has a 300-request/minute shared SQLite budget. Profile creation has per-caller limits of 5/minute and 20/hour plus a 10,000-profile capacity guard. Invalid recovery attempts have a per-caller 10/minute limit; a valid 256-bit code bypasses this invalid-attempt budget. Caller keys are salted HMACs of the trusted ingress IP, not stored raw addresses. Local loopback-only development uses a shared 200/minute creation budget. These bounds limit growth but are not a distributed abuse/DDoS solution. At public scale, add ingress abuse controls and define retention/capacity policy before raising limits. All SQL uses bound values. Errors omit exception bodies and credentials. No client code receives the NVIDIA key.

The server stores hashes of random 256-bit session and recovery capabilities, not their plaintext values. A recovery code grants profile access, works once and is replaced when a new code is generated. Recovery creates another session (at most ten per profile); it does not revoke other valid devices. Deleting a profile cascades to all its sessions and saves. Invalid/expired cookies do not silently create a replacement profile. Restore using a recovery code, or clear the expired cookie deliberately to start over. Profile switching binds each write to its original profile ID so an old editor cannot write into the newly recovered profile.

## Save consistency and versions

Each write carries the expected server revision and a unique mutation ID. The SQLite transaction increments the revision or returns 409 if another writer won; retrying the same last mutation returns its previous result. This is single-record compare-and-swap, not game-event merging. Profile IDs are unguessable identifiers, but authorization always comes from the session cookie.

Web Locks give one editor per game session across browser tabs. Without Web Locks, server revision checks still reject stale writes. Other games use independent browser cache keys. The cache retains confirmed and pending records for recovery, subject to browser quota. It never prunes another session during a save: a read/delete cleanup could race an editor in another tab. Explicit clear/profile-switch flows remove records with user intent. Progress fetches are read-only with respect to the cache, and re-read current local records after remote responses. An offline edit is stored locally and retried on reconnect or every 30 seconds while the page remains open. A network acknowledgement lost during concurrent edits can require manual conflict recovery. The conflict screen preserves a downloadable local copy and offers an explicit load-server-copy action. Never silently overwrite a newer server save. Clearing cookies/cache without keeping a recovery code can lose access; there is no email recovery.

Server history is capped at 60 sessions per profile. The browser displays its 60 most recent records; exact session lookup and JSON recovery export include every retained local record, independent of the display window. The local JSON export is for player-controlled backup and inspection; an arbitrary JSON import is not currently exposed. Existing browser-only v1 saves load and import when played. Export before switching profiles if there are unsynced edits.

Rule versions are separate from envelope and database schema versions. `gameReleases` defines current versions and daily activation dates. Views, engines, content, validators and PRNG behavior for v1 are retained explicitly. Resume links carry a version, and unknown versions cannot load or overwrite a save. When adding v2, retain v1 code, add a validator/loader and activation date, and test old-save fixtures. Never edit the historical catalogue or generator under the same rule version. The database currently has schema version 2; startup refuses a newer schema. Future migrations must be transactional, forward-versioned and tested against backups. Do not promise downgrade compatibility with newer schemas.

## Conservative profile lifecycle

New empty profiles are provisional. Creation and `npm run db:cleanup -- --apply` remove at most 100 eligible profiles per batch: inactive for 24 hours, no live session, no saved records, no recovery capability, and never promoted. `npm run db:cleanup` is a dry run. A saved game, issued recovery code or recovery promotes a profile permanently. Schema-1 profiles are retained during migration because their recovery expectations are unknown. Active, saved and recoverable profiles are never expired by this cleanup; the 10,000-profile guard can therefore still fill. Review capacity, privacy and retention with an operator before public launch. Distributed attackers and shared-IP fairness still require ingress controls; this is not comprehensive abuse prevention.

## Backups and tested restoration

The driver runs WAL with FULL synchronous commits and a five-second busy timeout. The database file is created mode 0600; its directory is 0700 when newly created. Verify permissions on an existing mounted directory and encrypt storage/backups according to deployment requirements. No encryption key is provisioned by this app.

1. Stop web and editorial writers for a coordinated recovery point; use both database paths from the application environment.
2. Run `npm run db:backup -- /secure/backups/fengi-YYYYMMDD`. The new bundle directory contains progress/editorial SQLite snapshots and a completion marker. Each snapshot uses SQLite's online backup API. Concurrent online snapshots are individually consistent, not atomic across both databases.
3. Run `npm run db:verify -- /secure/backups/fengi-YYYYMMDD`. Verification checks schemas, integrity, editorial digests and every retained v2 save's corresponding layout/state.
4. Run `npm run db:restore -- BUNDLE NEW_DIRECTORY`. It refuses an existing destination and verifies both copied databases. Preserve the old data and WAL/SHM sidecars; never overwrite active databases or mix old sidecars into the restored directory.
5. Point both `FENGI_DATABASE_PATH` and `FENGI_EDITORIAL_PATH` at the restored files while writers are stopped. Restart and verify health, recovery, saved games and published content. Later writes are absent from the restore. Rehearse this process on an isolated server. See EDITORIAL.md for retention and discovery-revocation semantics.

An operator must schedule backups, choose encrypted off-host storage, retention, recovery-point/time objectives and conduct periodic restoration drills. These are infrastructure responsibilities, not completed hosted services. Backups contain game answers and hashed credentials; restrict access. Profile deletion removes live records immediately; backup expiry must follow the chosen retention/privacy policy. Restoring an old backup can restore deleted profiles, so reconcile deletion records before reopening a restored production service. A durable off-host deletion journal is not implemented.

## Health and observability

`GET /api/health` checks database readability and reports `persistence: ready`; failure returns 503 without paths or secrets. It is a readiness signal, not a deep integrity or end-to-end write check. Put it behind host monitoring with restart/backoff policies; alert on sustained 503s, disk capacity and backup age. Database corruption/permission failures are not automatically repaired or replaced with an empty file.

API requests emit structured JSON with route name, status, duration and request ID. Responses include the same request ID. Logs deliberately exclude cookies, recovery codes, profile IDs, free-form answers and exception bodies. Monitor 5xx rates, 409 conflicts, 429 budget exhaustion and latency percentiles. No logs are exported to a third party by the application. Host/proxy logs may capture request URLs; never put credentials in URLs. Review failure traces before sharing: browser test traces can contain test recovery codes and game data.

## Content and release safety

LangChain/NVIDIA authoring remains an operator CLI, with no public inference endpoint. `NVIDIA_API_KEY` is server-only; private authoring defaults on, with `FENGI_AI_ENABLED=false` as an explicit disable switch. Both `NVIDIA_API_KEY` and `NVIDIA_MODEL` must be present in the executor’s secure environment; missing values produce a deterministic fallback without a provider call. The configured model is used without substitution. `npm run content:verify-live` makes two real calls, rejects fallback as failure and prints status/counts only; it never publishes or saves generated content. The adapter collects streamed chunks before validating or returning a complete draft. It accepts bare JSON or one enclosing JSON code fence; surrounding prose and schema violations still fail. Requests use a 4,096-token budget shared by reasoning and final content, a default 60-second timeout and 90-second total abort (bounded overrides via `NVIDIA_REQUEST_TIMEOUT_MS`) and at most one retry. `NVIDIA_REASONING_EFFORT` defaults to `low` for short editorial drafts; `medium`, `high` and `none` are explicit overrides subject to provider support. The hosted endpoint rejected `none` during live verification despite listing it in its API reference; `low` follows the model card and was accepted. Unsupported modes, length-truncated responses and invalid content fall back without exposing provider details. Invalid output/provider failures return reviewed deterministic categories. A real key, authorized provider access and production/model rights review remain necessary for live verification. Odd Answer v1 contains eight curated categories; new content requires a new rule edition when it changes historical puzzles.

CI runs lint, types, engine/version/save/database tests, dependency audit, production build and desktop/mobile browser flows including recovery, concurrent tabs, API boundaries and network interruptions. Before public launch: real Safari/Android and screen-reader review, device/load profiling, host-specific CSP/TLS/security review, editorial rights review, retention/privacy policy and backup/restore drills. CI does not deploy; the obsolete Alchemy Arena Pages workflow has been removed.

Keep immutable artifacts tagged with commit IDs and a verified backup before schema changes. Roll back only to an application compatible with the active database and rule versions. Audit the root lockfile for the current app. Historical default-branch alerts may remain until repository scanners observe the removal of the obsolete app; deletion from this feature branch does not establish their resolution on the default branch.
